# Baru Budget v0.13 — Mobile UX and Hardening

## Status

IN_PROGRESS — architectural analysis approved on 2026-09-07 (`docs/ARCHITECTURE_ANALYSIS_V0.13.md`); implementation complete and deployed. No migration was needed. Manual verification and the production check are pending.

## Objective

Make Baru Budget ready for daily use on a phone and resistant to failure, without adding any feature. Every screen answers whether it is loading, whether it failed and whether it is empty; everything clickable is reachable by keyboard; the home stops firing nine queries; and the permission matrix is proved by test on every table.

## Scope

- A written audit of the twenty screens, delivered with the first fix, which is the real scope of the version.
- Responsiveness: the three table-only screens become lists on a phone; the twenty-one stylesheets without a media query are reviewed; no screen scrolls horizontally.
- One contract for loading, error and empty, applied everywhere, including the three detail screens that handle no error today.
- Accessibility: keyboard on everything clickable, visible focus, textual labels on charts, live regions, contrast checked, reduced motion respected.
- Errors: one message vocabulary, no database code on screen, no silent failure.
- Performance: the home stops loading what it does not show; DEBT-002 is closed with real pagination; the bundle stays inside its budget.
- Permissions and row level security: a matrix test covering every table, not only the recent ones.
- No schema migration planned; a gap found by the matrix becomes its own documented migration.

## Technical Behavior

The analysis recorded the measured starting point: twenty-one of forty-three stylesheets have no media query, three screens use a table as their only interface, three detail screens have no error branch, two amortization tables have mouse-only rows, the dashboard injects seven stores and opens about nine queries, and transactions still load with a fixed limit of one thousand rows.

- **A month is never truncated.** `readAllPages` walks the pages until one comes back short, building a fresh query per request instead of reusing an executed builder. DEBT-002 is closed: a list silently cut at one thousand rows showed wrong totals with no warning.
- **A row that behaves like a button is one.** `data-rows` gives an actionable row `role="button"`, `tabindex="0"` and Enter and Space, on the table and on the phone cards alike.
- **The phone drops columns instead of scrolling.** Secondary columns are omitted from the cards, and every card field carries its column label, so nothing is guessed from position.
- **Loading is answered once.** The progress bar only shows before the first load, so a refresh never blanks a screen that already has content.
- **The stores load on demand.** A `resource()` whose params return undefined does not fetch, so a store stays idle until a screen asks. The dashboard asks only for what it will show.
- **The permission matrix is generated, not written by hand.** A table without row level security, without a policy, or missing one of the four commands on an owned table fails the matrix immediately.

## Database Changes

None planned. A gap found by the row level security matrix would become its own migration and be recorded as a fixed bug.

## Security Changes

- `rls_matrix.test.sql` asserts, over every table in `public`: row level security enabled, at least one policy, all four commands covered on any table with an owner column, and no policy granted to `anon` or `public`.
- The six roles of section 61 are exercised on the current model: owner, VIEW, MANAGE, unrelated user, transitive grant and MANAGE attempting to change grants.
- No gap was found, so no corrective migration was needed.
- `describeDataError` is covered by a test that fails if a database code or an internal message ever reaches the screen.

## Known Limitations

- The manual verification is not done: screen reader, full keyboard walk, the twenty screens at three widths and the contrast check are listed as unchecked in the audit. Automated tests prove the structure, not the experience.
- v0.13 has not been checked in production yet.
- Pagination is proved by unit test; no real month above one thousand transactions exists yet to exercise it end to end.
- `InstallmentsStore`, `SettlementsStore` and `CardsStore` still load eagerly, because they have consumers outside their own screens. Only the two stores used solely by their feature and the home were gated.
- Nineteen stylesheets have no media query by design; the audit records why for each.

## Out of Scope

Visual redesign, new features, switchable light and dark theme, internationalization, progressive web app and offline use, notifications, browser end-to-end tests, continuous integration which belongs to v1.0.
