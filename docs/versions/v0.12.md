# Baru Budget v0.12 — Baru Budget Excel Format v1

## Status

IN_PROGRESS — architectural analysis approved on 2026-09-07 (`docs/ARCHITECTURE_ANALYSIS_V0.12.md`); implementation complete and `main` deployed on 2026-09-07. No migration was needed. Production check pending.

## Objective

Freeze the first official Baru Budget Excel Format: a versioned, human readable workbook the user exports, edits in Excel and imports back without duplicating anything. Re-importing an untouched export must change nothing.

## Scope

- One declarative round-trip contract consumed by both the export and the import.
- Workbook with an `Info` sheet (metadata), a `Legenda` sheet (accepted values) and the data sheets.
- Complete paginated export of the current context owner, producing the backup file.
- Import with a mandatory preview: new, updated, unchanged and invalid rows, with the invalid ones detailed.
- Stable UUID identity: a known id updates, an unknown id inserts, an empty id creates.
- Absence never deletes.
- Friendly and technical columns side by side; a name resolves the link only when the id cell is empty.
- `Configurações → Dados` page with export, import, preview and result.
- Vitest coverage of the contract, the classification and the full write/read round trip.

## Delivered

- `workbook-schema.ts`: the frozen version 1 contract. Eleven sheets in dependency order, every column declaring its key, label, type, role and database field, plus the forbidden fields the format never carries.
- `workbook-info.ts`: `Info` metadata, compatibility check and the `Legenda` sheet listing every accepted enum value, every read-only column and how a name resolves a link.
- `workbook-model.ts`: pure builder that turns rows plus catalogs into the workbook, including the backup file name.
- `excel-io.ts` and `workbook-file.service.ts`: the only place that knows a file format exists, loaded through dynamic `import()` so the initial bundle never carries the libraries.
- `import-parser.ts`: file to rows keyed by the contract, ignoring sheets the contract does not know.
- `import-plan.ts`: pure cell parsing, name resolution, reference checking and classification into new, updated, unchanged and invalid, with catalogs extended as earlier sheets are planned.
- `catalogs.ts`: id to name for the export and name to id for the import, built once from the same rows.
- `data-snapshot.ts`: one paginated read of everything, shared by the export and the preview.
- `data-transfer.repository.ts`: paginated reads split by whether the table carries an owner, batched upserts and the allocations RPC. It exposes no delete.
- `export.service.ts`, `import.service.ts` and `data-transfer.store.ts`.
- `data-page`: `Configurações → Dados` with export, file picker, preview, invalid-line detail and result.
- Dependencies `write-excel-file` 4.1.1 and `read-excel-file` 9.3.10.
- Version `0.12.0` in `package.json` and `environment.appVersion`.
- Vitest: 60 files, 368 tests. pgTAP: 31 files, 890 assertions.

## Technical Behavior

Everything runs in the browser under the user's session so row level security decides every write; the workbook carries no `owner_user_id` and no audit columns; parcels and settlements are transactions and have no sheets of their own; groups and people are exported for readability and are not importable; enums travel with their database value and are documented in the `Legenda` sheet; a name resolves a link only when the id is empty and never creates a record; unchanged rows are compared field by field and produce no write; no import path issues a delete; allocations are imported through `set_transaction_allocations`; the import is idempotent and applied sheet by sheet in dependency order rather than in a single transaction.

- **The workbook is not authority.** The owner of every written row comes from the current financial context, and the applier drops the forbidden fields even if something put them in the plan. A test asserts that a file carrying `owner_user_id` cannot change who owns the record.
- **Two steps, always.** Reading and classifying produce a plan; only an explicit confirmation applies it. The confirm button stays disabled when the file is identical to the database.
- **Unchanged rows are compared per field type**, so a numeric column compares by value and a text column compares literally. A round trip with no edits produces zero writes.
- **A read-only context can export and cannot import**, in the interface and in the database.

## Database Changes

None planned. The format is built on the existing schema and adds no migration.

## Security Changes

- The format has no `owner_user_id` column and no audit columns, so a spreadsheet cannot claim ownership or rewrite history.
- No sheet reaches grants, household membership or any credential, so section 49 has nothing to leak.
- `Grupos` and `Pessoas` are exported for readability and are not importable; people carry id and display name only, never an email.
- The import writes exclusively through the authenticated client, so row level security decides every row, and allocations go through `set_transaction_allocations` so the deferred sum invariant is never bypassed.
- No import path issues a delete: absence in the file is reported as a kept count.
- A new pgTAP block asserts that a VIEW grantee cannot insert into any table the format writes.

## Known Limitations

- The Excel format has not been checked in production yet; the behaviour is verified by tests and on the local stack only.
- The import is idempotent, not transactional: a failure in one sheet leaves the earlier sheets written, and running the file again finishes the job.
- The preview cannot tell that a row id belongs to another owner, because row level security hides that row; the database refuses the write and the result reports it. References to accounts, categories, cards, groups and people are checked in the preview.
- A name never creates a record: an unknown or ambiguous name invalidates the row.
- Deletion through the spreadsheet does not exist.
- Export always covers the whole owner, never the selected period.

## Out of Scope

JSON export, scheduled backups, cloud upload, importing third-party or legacy spreadsheets, deletion through Excel, importing permissions, groups or profiles, schema version 2 and its converters.
