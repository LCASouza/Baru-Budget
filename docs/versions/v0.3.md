# Baru Budget v0.3 — Transactions

## Status

DELIVERED — 2026-09-06. All completion criteria met; production validated by the administrator.

## Objective

Record real finances: incomes, expenses and transfers between the user's own accounts, with account and category management, basic filters, per-account balance split between money and benefits, and a period summary. Architecture reference: `docs/ARCHITECTURE_ANALYSIS_V0.3.md`.

## Scope

- Database: `transaction_status` enum, `transactions` table (INCOME, EXPENSE, TRANSFER), cross-table validation trigger, `account_balances` view, owner-only RLS, audit defaults, local seed data, regenerated types.
- Transactions page: tabs Todas / Entradas / Saídas, filters (category, account, status, description search), period summary, list grouped by day, create, edit and delete.
- Transaction form bound to real data, with transfers, status and due date.
- Accounts: list with current balance, money and benefit totals, create, edit, activate/deactivate, delete.
- Categories: list by kind, create, edit, activate/deactivate, delete.
- Settings page with Contas, Categorias and Perfil tabs (display name editing).
- Global month period shared by the header and the pages.
- pgTAP and Vitest tests for rules, integrity, RLS, balances, dates, amounts and filters.
- Migrations applied to the hosted project before the frontend deploy.

## Technical Behavior

- `amount` is always positive; `kind` gives the direction. INCOME credits `account_id`; EXPENSE debits it; TRANSFER debits `account_id` and credits `destination_account_id`.
- Stored statuses are PENDING, PAID and CANCELLED (default PAID). OVERDUE is derived at read time: `status = PENDING` and `coalesce(due_date, date) < today`. Labels follow the kind (`transactionStatusLabel`): expenses Pendente / Vencido / Pago / Cancelado; incomes Pendente / Atrasado / Recebido / Cancelado; transfers Pendente / Atrasada / Efetuada / Cancelada. The status filter uses the labels of the active tab and "Pago / Recebido" under Todas.
- `account_balances.current_balance = opening_balance + PAID movements`; PENDING and CANCELLED never move money. The period summary (Entradas, Saídas, Saldo do período) counts PAID and PENDING incomes and expenses of the loaded month, ignores CANCELLED and TRANSFER, and follows the active filters.
- Money totals: active accounts with type BANK, CASH or OTHER; benefit totals: active BENEFIT accounts. Inactive accounts keep their balance but leave the totals and the form selectors.
- `validate_transaction_references()` (before insert/update, invoker rights) requires the category and both accounts to belong to `owner_user_id` and the category kind to match the transaction kind. Rows hidden by RLS count as missing, so the operation fails closed with `23503`/`23514`. Because the trigger runs before the policy `with check`, an attempt to insert or reassign a transaction to another owner fails in the trigger rather than in the policy; both outcomes deny the write.
- `on delete restrict` on `category_id`, `account_id` and `destination_account_id`: deleting a referenced account or category fails with `23503`; the interface maps that code to a message suggesting deactivation.
- Transactions are loaded per month (`date between start and end`, ordered by `date desc, created_at desc`, limit 1000). Tabs, filters and search are applied on the client. Category and account names are resolved from the stores' `byId` maps instead of PostgREST embedding.
- Dates travel as `yyyy-MM-dd` built from local date parts; amounts are parsed from `1.234,56`, `1234,56`, `12` and `12.5` (a single dot with one or two decimals, produced by numeric keyboards without a comma).
- Every store is a root service built on `resource()` keyed by `AuthService.userId` (and the period for transactions); they clear on logout and reload after each mutation. `TransactionsStore` also reloads the balances after a mutation.
- The `kind` query parameter selects the tab (`/transactions?kind=INCOME`); switching tabs resets the category filter. On mobile the filters collapse behind a button that shows the count of active filters.
- The transaction form disables saving while there is no active account and points to `/settings/accounts`. Inactive categories and accounts stay selectable only in a transaction that already uses them.
- `created_by`/`updated_by` default to `auth.uid()` on `categories`, `accounts` and `transactions`, so the generated `Insert` types no longer require them; the audit triggers still override client values.

## Security Changes

- RLS enabled on `transactions` with select/insert/update/delete restricted to `authenticated` and to the owner (`with check` on insert and update).
- Ownership of referenced categories and accounts enforced by trigger; category kind enforced by trigger; SETTLEMENT blocked by constraint; transfer shape enforced by constraint.
- `account_balances` runs with the caller privileges; `rls_enabled.test.sql` now requires `security_invoker` on every view in `public`.
- Post-login data access verified through PostgREST with the local development user: anonymous requests to `account_balances` return an empty list; the wrong-kind category is rejected with `23514`.

## Known Limitations

- The dashboard and the context selector keep mock data until v0.5 and v0.4.
- A month with more than 1000 transactions is truncated by the PostgREST row limit.
- Account and category colors and icons are stored but not editable in the interface.
- The overdue state is computed with the browser date at load time; a page open across midnight updates on the next reload.

## Out of Scope

SETTLEMENT, `household_id`, grants and household policies, real dashboard, credit cards and expense origin, installments, recurrences, custom date ranges, person and household filters, import/export.
