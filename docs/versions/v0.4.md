# Baru Budget v0.4 — Households and Sharing

## Status

IN_PROGRESS — architectural analysis delivered (`docs/ARCHITECTURE_ANALYSIS_V0.4.md`); implementation awaits approval.

## Objective

Share finances in two distinct ways: households, where people take part in a common financial set, and personal access grants, where a user gives another user VIEW or MANAGE access to their own finances. Every rule is enforced by the database, access is never transitive and managing finances never includes managing security.

## Scope

- Database: `households`, `household_members`, `financial_access_grants`, enums, authorization functions (`can_view`, `can_manage`, `is_household_member`, `is_household_admin` and helpers), `transactions.household_id`, complete policies replacing the owner-only ones on `accounts`, `categories`, `transactions` and `profiles`, e-mail lookup function, last-admin guard, local seed with a second user.
- Real financial context in the header (personal, households, finances shared with me), persisted per browser; accounts, categories and transactions stores follow the context.
- Transactions: "Grupo" field, household context listing (who registered, category, no accounts), read-only mode for VIEW and for other members' entries, created/updated by shown when different from the owner.
- Accounts and categories in a shared context: read-only under VIEW, manageable under MANAGE.
- Households page: create, rename, add member by e-mail, change role, remove, leave.
- Sharing page: grant VIEW or MANAGE by e-mail, change permission, revoke; list of finances shared with me with a shortcut to open the context.
- pgTAP tests for every scenario of MASTER_PROMPT section 61 and Vitest tests for context, stores, pages and forms.
- Migrations applied to the hosted project before the frontend deploy.

## Known Limitations

- The dashboard keeps mock data and ignores the context until v0.5.
- Members are added by exact e-mail lookup; there is no invitation flow.
- Households have no categories or accounts of their own.

## Out of Scope

Dashboard by context and charts, transaction allocations and settlements, invitations with acceptance, household-owned categories or accounts, additional roles, full audit log, notifications.

## Completion Criteria

- `npm run db:reset` applies all migrations; `npm run db:types` produces no diff.
- `npm run test:db`, `npm test`, `npm run lint` and `npm run build` pass.
- Every table in `public` has RLS enabled; no policy for `anon`; every `security definer` function is not executable by `anon`.
- pgTAP covers: owner OK; VIEW select OK and write denied; MANAGE select and write OK; unrelated user denied; transitive grant denied; MANAGE altering grants denied; household member sees household transactions only; non-member denied; revoked grant and inactive member lose access.
- Migrations applied to the hosted project; `households`, `household_members` and `financial_access_grants` return an empty list to the publishable key.
- In production with two users: create a household, add the second user, tag a transaction with the household and see it as the other user; grant VIEW and confirm read-only access; switch to MANAGE and edit; revoke and confirm the loss of access.
- `docs/versions/v0.4.md` and `docs/PROJECT_STATUS.md` updated; version marked DELIVERED only after all criteria are met.
