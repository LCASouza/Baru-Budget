# Baru Budget v0.8 — Recurrences

## Status

IN_PROGRESS — implementation complete locally (build, lint, Vitest and pgTAP passing); hosted migrations and production check pending.

## Objective

Register what repeats every month and turn it into real transactions: fixed expenses and recurring incomes, with monthly instances that can be edited without changing the template. Architecture reference: `docs/ARCHITECTURE_ANALYSIS_V0.8.md`.

## Scope

- Database: `recurrence_frequency` enum, `fixed_expenses` and `recurring_incomes` tables, recurrence columns on `transactions`, shape constraint, partial unique indexes, `generate_recurrences`.
- Explicit generation per month, idempotent, with no scheduler.
- Fixed expenses page with two tabs, the status of each template in the selected month and a generate action.
- Monthly instances editable as ordinary transactions.
- Recurrence mark in the transactions list.
- pgTAP and Vitest tests.
- Migrations applied to the hosted project before the frontend deploy.

## Technical Behavior

- **Two tables, on purpose.** `fixed_expenses` and `recurring_incomes` are kept apart as the specification requires. The unified `RecurrenceTemplate` exists only in the interface, so the list, the form and the store are not duplicated.
- **The monthly instance is an ordinary transaction.** It shows up in the transactions list, counts in the period, respects row level security and can be edited, cancelled or deleted. Adjusting the amount of one month never touches the template, which keeps its suggested amount.
- **Generation is explicit and idempotent.** `generate_recurrences(owner, month)` creates the missing instances of one month and returns how many it created. The partial unique indexes on (template, competence month) plus `on conflict do nothing` make a second run create nothing. A deleted instance is recreated; a cancelled one still occupies the competence and is not recreated silently.
- **Dates and status.** An account fixed expense is generated as PENDING with the due day clamped to the month. A card fixed expense is generated as PAID and the existing trigger routes it to the right invoice, exactly like any card purchase. A recurring income is generated as PENDING on its receipt day.
- **Frequencies.** Monthly templates generate every month; yearly ones only in their reference month, which is required by constraint. The three-valued logic of SQL is handled explicitly, so a yearly template without a reference month is rejected.
- **Invoker rights.** Generation runs with the caller privileges: VIEW cannot generate, MANAGE generates for the owner and is recorded in `created_by`.
- **Deleting a template keeps history.** The link on the generated transactions becomes null and they remain as ordinary transactions; the competence month is kept as historical information.
- The templates carry an origin validated against the owner: category of the right kind, account, card and household membership.

## Security Changes

- Generation runs with invoker rights, so row level security decides each insert; covered by pgTAP with VIEW and MANAGE.
- Template references are validated against the owner: an account, card or category of another user is rejected with `23503`, and a category of the wrong kind with `23514`.
- The shape constraint refuses a template link without a competence month, two templates at once, a competence month that is not the first day, and a template backing the wrong kind.
- `generate_recurrences` and the assertion helpers are not executable by `anon`.
- Verified through PostgREST on the local stack: generating the current month again creates nothing, generating the next month creates five instances, and `anon` is denied.

## Known Limitations

- Generation is triggered by the user for a chosen month; there is no scheduler.
- Only monthly and yearly frequencies are supported.
- Future months are only projected by generating their transactions.
- Editing a template never rewrites instances already generated.

## Out of Scope

Scheduled generation, weekly and custom frequencies, programmed amount adjustments, projections without transactions, splitting instances between people, loans and financings, due date notifications.
