## Technical Behavior

The analysis recorded the measured starting point: no continuous integration exists, so a push with a broken test publishes anyway; the README still claims v0.10; twenty-two of forty-seven functions in `public` are `security definer`; no private key is versioned and the Angular code never mentions `service_role`; and ten versions carry a deferred production check.

- **The gate exists now.** A push to `main` runs the four commands. Protecting the branch with that check is a setting on GitHub and remains an administrator action.
- **The review became tests.** Three transversal files hold for anything added later: `rls_matrix` over every table, `security_surface` over every function, `view_isolation` over every view. A table, function or view added without its policy, grant or isolation fails the suite instead of waiting for the next review.
- **The finding was hardening, not a hole.** Six trigger functions kept the default grant. A direct call already failed with "trigger functions can only be called as triggers", confirmed as `anon`, so nothing was exposed. After the migration those functions are not even in the PostgREST schema cache: the hosted project answers `PGRST202` instead of exposing them.

## Bugs Found

| ID | Description | Severity | Status |
|---|---|---|---|
| BUG-003 | Six trigger functions kept the default execute grant while the ones written from v0.8 onwards were revoked, leaving surface with no purpose. A direct call already failed, so nothing was exposed. | Hardening | FIXED |
| BUG-004 | Creating a household failed from the application with `42501`. The client reads the new row back in the same call, and the trigger that makes the creator a member of it runs after that read, so the read policy could not see the row yet. The whole households feature could not be started from the interface. | Blocking | FIXED |
| BUG-005 | A card purchase is accepted with a `date` later than its own `invoice_due_date`, which cannot happen: a purchase always precedes the invoice that charges it. Found when an import carried 37 instalments whose competence had been shifted past their invoice, and nothing in the database refused them. | Hardening | FIXED |
| BUG-006 | Editing a loan or a financing left every instalment already generated on the old amounts and dates. `generate_*_schedule` only inserts what is missing, so the screen showed an outstanding balance derived from the edited record next to a total to pay summed from stale transactions, with nothing saying they disagreed. | Blocking | FIXED |

## Bugs Fixed

- BUG-005, by `20260908150100_card_purchase_before_invoice.sql`. The rule allows equality, because a due day just past the closing day makes both land on the last day of a short month, and it covers purchases only: an invoice payment is a transfer whose date may fall after the due date, since being late is a fact to record.
- BUG-006, by `20260908150200_realign_schedules.sql`, which adds `realign_loan_schedule` and `realign_financing_schedule`. Realigning is a separate operation instead of part of generating, because folding it in would silently overwrite an instalment corrected by hand to the amount actually charged. Only `PENDING` instalments move; a paid one records money that already left the account and a cancelled one records a decision. `instalmentDrift` reports the divergence and both pages show it beside the totals with an action to fix it.
- BUG-003, by `20260907230100_function_grants.sql`, guarded from here on by `security_surface.test.sql`.
- BUG-004, by `20260908010100_household_creator_visibility.sql`, which adds `create_household`: it writes the household, lets the trigger add the membership, and only then reads the row back. The read policy was deliberately left untouched, because widening it to the creator would also let someone removed from a household they created keep seeing it. Guarded by `households.test.sql` and by `household.repository.spec.ts`, which fails if creation ever goes back to a plain table insert.

## Known Limitations

- The ten deferred production checks are open. The version is not DELIVERED until they are closed, and only the administrator can close them.
- Protecting `main` with the continuous integration check is a GitHub setting and has not been done.
- Backup and import/export are validated against the hosted project with real family data since 2026-09-08.
- Drift detection compares amounts only. Moving the first due date shifts competences without touching amounts and is not reported, though realigning corrects both.
- There is no staging environment, no production monitoring and no browser end-to-end test. All three are deliberate.

## Out of Scope

Everything listed in MASTER_PROMPT section 65 (Open Banking, bank integration, Pix, investments, native apps, multi-currency and the rest), staging environments, production monitoring and telemetry, browser end-to-end tests, third-party data migration.
