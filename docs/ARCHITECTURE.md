# Baru Budget — Architecture

The system as it is, not as it was planned. The thirteen analyses in `docs/` remain the history of why each decision was made; this file describes the result. `docs/MASTER_PROMPT.md` is the specification and outranks this document.

## 1. Shape

```
Angular 22 (browser)  ──►  Supabase PostgREST  ──►  PostgreSQL 17
   publishable key            row level security       policies, constraints, functions
        │
        └── Cloudflare Pages, automatic deploy from `main`
```

There is no backend of our own. The browser talks to PostgREST with the user's session, and every decision about who may read or write a row is taken by the database. The interface is not a security authority: hiding a button is not denying access.

## 2. The two rules that shape the data model

**Money is never stored twice.** Anything derivable is derived: account balances, credit card invoices, monthly totals, instalment progress, balances between people, and the outstanding balance of a loan or a financing. They are views or pure functions, never columns kept in sync by hand.

**One kind of row for one kind of event.** A transaction is a transaction whether it came from a card purchase, one instalment of twelve, a generated recurrence, a loan instalment or a settlement between two people. Because of that, every feature written afterwards works on all of them without a special case.

## 3. The transaction

`transactions` carries four kinds — income, expense, transfer and settlement — and one shape constraint that decides which columns each kind may fill. The origin of a row is a link, not a kind:

| Link | Meaning |
|---|---|
| `credit_card_id` + `invoice_due_date` | A card purchase, or the payment of an invoice |
| `installment_group_id` + number + count | One instalment of a purchase |
| `fixed_expense_id` / `recurring_income_id` + `recurrence_month` | One generated month of a template |
| `counterparty_user_id` + `settlement_direction` | A settlement between two people |
| `loan_id` + `loan_installment_number` | The disbursement or one instalment of a loan |
| `financing_id` + `financing_installment_number` | The down payment or one instalment of a financing |

Three consequences worth knowing:

- **A card purchase has no account.** The money leaves when the invoice is paid, and paying the invoice is a transfer. Double counting is impossible by shape, not by adjusting a report.
- **A loan disbursement is an income excluded from the monthly income totals.** Cash goes up without the month looking richer.
- **A financing has no income at all**, because the bank pays the seller directly. The asset value never becomes a transaction: only the down payment and the instalments do, which is how an acquisition and its instalments cannot be counted twice.

## 4. Generation is idempotent

Instalments, recurrences and debt schedules are generated by explicit user action, never by a scheduler, because none exists. Every generator writes with `on conflict do nothing` behind a partial unique index, so running it again creates nothing. A deleted row comes back; a cancelled one keeps its number and stays cancelled.

The generators run with invoker rights, so row level security decides each insert: a reader cannot generate for an owner they can only view.

## 5. Access

Three contexts: your own finances, a household, and another person's finances shared with you.

- `financial_access_grants` gives one person VIEW or MANAGE over another's data.
- `households` and `household_members` group transactions that belong to a shared ledger.
- Two `security definer` functions answer every policy: `can_view(owner)` and `can_manage(owner)`.

A grant is **not transitive**: only a grant made directly to the current user counts. Someone who manages your finances cannot pass that on, and cannot create grants on your behalf.

The counterparty of a split or a settlement can read exactly the transaction that involves them, and nothing else of that owner.

## 6. Invariants live in the database

- Constraints for shape and range, on every table.
- Deferred constraint triggers where a rule spans rows: the allocations of a transaction must sum to its amount, checked at the end of the statement so a split can be replaced atomically.
- Triggers that fill `created_by` and `updated_by` from the session, so audit cannot be forged.
- Triggers that validate every reference against the owner: an account, a category or a card belonging to someone else is refused before any policy is consulted.

## 7. Money and dates

Amounts are `numeric(14,2)` in the database and are handled in integer cents in the client, so no sum drifts. Interest and instalments are computed in cents with the rounding difference landing on the last instalment, in the database and in the client, from the same table of cases.

Dates travel as `yyyy-MM-dd` strings and are read in the local time zone, never through `toISOString`, so a date never shifts by a day. The interface shows `dd/MM/yyyy` and `R$ 1.234,56`.

## 8. The client

Feature folders under `src/app/features/`, each with its repository, its store and its screens. A repository is the only place that talks to Supabase. A store owns the state of a feature through signals and `resource()`. Screens read stores and never call the database.

Shared pieces that carry a rule rather than a widget:

| Module | Rule it carries |
|---|---|
| `shared/finance/amortization.ts` | Price, SAC and simple interest, mirroring the database functions |
| `shared/supabase/paginate.ts` | A list is read to the end, never truncated at the PostgREST cap |
| `shared/components/async-state` | Every screen answers loading, error and empty |
| `shared/components/data-rows` | A table on the desktop is a list of cards on a phone |
| `shared/money`, `shared/dates`, `shared/format` | Cents, local dates and the display format |

## 9. The Excel format

`Baru Budget Excel Format`, schema version 1, frozen. One declarative contract in `features/data-transfer/workbook-schema.ts` drives both the export and the import, so the two cannot drift.

The workbook carries no `owner_user_id` and no audit columns: the owner comes from the session. Reading and classifying produce a plan; only an explicit confirmation applies it. Absence never deletes, unchanged rows produce no write, and allocations are imported through the same function the split dialog uses.

## 10. Tests

- **pgTAP** covers the database: financial rules, dates, invoices, interest, allocations, settlements, recurrences and permissions. Three files are transversal and hold for anything added later: `rls_matrix` (the permission matrix over every table), `security_surface` (search paths, grants, audit) and `view_isolation` (each view isolates owners).
- **Vitest** covers pure calculations, stores, and the components that carry a rule.
- **Continuous integration** runs lint, build, Vitest and pgTAP on every push to `main`.

## 11. Environments

Local development runs the Supabase stack in Docker with a seeded database. Production is the hosted Supabase project plus Cloudflare Pages, which builds from `main`. There is no staging.

Migrations are applied to the hosted project with `npx supabase db push` before the frontend that needs them reaches production.
